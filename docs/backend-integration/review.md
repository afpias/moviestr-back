# Проверка плана backend Moviestr

Дата: 2026-10-27. Статус: проверка завершена, проектирование до реализации.

## Что проверено

- Прочитаны `spec.md`, `plan.md`, `tasks.md` из этого пакета.
- Прочитаны связанные SPEC-001, SPEC-002, SPEC-003, SPEC-006, SPEC-007, дополнительно SPEC-004 и SPEC-005.
- Сверены реальные DTO, правила матча, каталог, процентили, ранжирование и OCR в соседнем `moviestr-front`.
- Код и настройки фронтенда не изменялись. В backend сейчас есть документация; package.json, реализация и `.git` отсутствуют.
- Node.js v24.21.0, npm, Yarn и Docker CLI доступны. Наличие Docker CLI пока не подтверждает доступность engine или PostgreSQL.

## Оценка

Порядок этапов и серверная модель из SPEC-009 подходят. План правильно выделяет транзакции, персональные проекции,
устойчивые дедлайны и подготовку вне DB locks. Нужны уточнения контрактов и восстановления ниже; писать backend
как прямую копию browser demo нельзя.

## Подтверждено владельцем

- Локальный Docker Compose, затем один сервер; hosting выбрать позже без создания внешних ресурсов сейчас.
- HTTP-команды + native WebSocket, HttpOnly guest cookie + одноразовый WS-ticket; без Redis.
- Общая cookie означает одного гостя; независимые игроки используют разные контексты/устройства.
- `pg` и SQL без ORM.
- Проверка соло по `movieId`, восстановление неверных попыток, `w1280`, выдача только текущего кадра, сохранение OCR fallback.

## Оставшиеся решения владельца

- Сроки хранения: предложены 30 дней гостевой сессии с продлением при активности, 7 дней завершённых игр/комнат и
  неактивного соло; dedup хранится до удаления родительской сущности. Владелец подтвердил эти сроки.
- Package manager и конвенции: Yarn Classic и оформление инструментов как у фронта подтверждены владельцем.
- Конкретные hosting и production origins отложены по решению владельца. Они не мешают локальной реализации.

## Независимая проверка проектирования

Ревьюер проверил итоговый дизайн до реализации. Уточнены три места: presence ограничивается подпиской на конкретную
комнату; waiting membership освобождается после grace; preparation retry создаёт новую operation/generation,
а dedup replay сохраняет исходный HTTP outcome. Эти решения внесены в дизайн как решения исполнителя.
Дополнительных существенных вопросов по скрытию ответа, SQL locks и описанным расширениям DTO не осталось.

## Как уточнить этапы

1. Зафиксировать утверждённый дизайн, HTTP/WS DTO и модель SQL; подготовить runtime, миграции, cookies и валидацию.
2. TMDB и каталог: RU/EN, percentiles, пять кадров, OCR, cache/timeouts, исключение повторов.
3. Соло: переходы, ID matching, восстановление, idempotency, private projections.
4. Лобби: preview, пароль, join/start/leave, unique nicknames, race последнего места.
5. Матч: очки, личные кадры, distinct movies, deadline, атомарный переход к следующему фильму.
6. WS/scheduler/outbox: presence, host transfer, leases, restart, гонки и ограничение доступа.
7. OpenAPI JSON, схемы WS, fixtures, env example, инструкции запуска и отчёт проверки.

Полноценные frontend E2E после подключения и ручная проверка на двух физических устройствах остаются отдельной приёмкой.
Backend handoff проверяет реальные HTTP/WS-клиенты с независимыми cookies и PostgreSQL.

## Первичные технические источники

- [NestJS WsAdapter](https://docs.nestjs.com/websockets/adapter): native browser WebSocket и формат `{event,data}`.
- [PostgreSQL explicit locking](https://www.postgresql.org/docs/current/explicit-locking.html): row-level locks и единый порядок их получения.
