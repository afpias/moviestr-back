# Moviestr backend: правила работы

## Границы проекта

- Этот каталог содержит отдельный backend Moviestr на NestJS, TypeScript и PostgreSQL.
- Читать исходную задачу и `docs/backend-integration/{spec,plan,tasks}.md`, затем связанные спецификации.
- Документы фронтенда сейчас находятся в `docs/`. Пути `reference/frontend-docs` и `Projects/vue` из исходного поручения устарели.
- Существующий фронтенд находится рядом в `../moviestr-front`. Его код можно читать для проверки контрактов,
  но изменять, подключать к API и удалять demo runtime следует только на отдельном этапе по запросу владельца.
- Прямые указания владельца имеют приоритет. Предложения из документов не считать принятыми решениями без подтверждения.

## Принятые технические решения

- NestJS + strict TypeScript; PostgreSQL через `pg` и SQL, без ORM.
- Локальный запуск через Docker Compose; первая версия рассчитана на один постоянно работающий backend instance.
- HTTP-команды и native WebSocket; гостевая HttpOnly cookie и одноразовые короткоживущие WS-tickets.
- Две вкладки с общей cookie представляют одного гостя. Независимые игроки используют разные браузерные контексты или устройства.
- Соло и мультиплеер проверяют выбранный `movieId`; неверные попытки восстанавливаются после refresh.
- Игровые кадры имеют размер `w1280`; клиент получает только текущий открытый кадр. OCR допускает предусмотренный спецификацией fallback.
- Redis, Socket.IO, аккаунты, OAuth, чат, дополнительные режимы и платные AI API в scope не входят.
- Конкретный hosting, production topology и создание внешних ресурсов пока не согласованы.

## Архитектура и код

- Использовать Nest-модули по ответственности: sessions, tmdb, catalog, solo, rooms, realtime, scheduling, database, common.
- Controllers и gateway проверяют транспорт; services координируют сценарии; чистые domain-функции определяют игровые переходы;
  repositories инкапсулируют SQL и транзакции. Frontend FSD в backend не переносить.
- Внешние данные принимать как `unknown` и проверять на границе. Не использовать `any` и необоснованные type assertions.
- SQL выполнять с параметрами. Изменения схемы оформлять последовательными SQL-миграциями; не переписывать применённые миграции.
- Игровую команду, изменение версии и запись идемпотентности сохранять атомарно. Блокировать корневую строку игры или комнаты;
  соблюдать одинаковый порядок блокировок в HTTP, scheduler и worker.
- Не выполнять TMDB, OCR или другие сетевые операции под блокировкой БД. Использовать ограниченные lease с generation fencing.
- DTO собирать явной проекцией: не сериализовать строки БД или внутреннюю модель фильма напрямую.
- Код и идентификаторы писать на английском, документацию — на русском. Не оставлять отладочные `console.log`.

## Безопасность и контракты

- Backend определяет фильм, правильность ответа, кадры, очки, deadline и права хоста.
- Чужой `participantId`, никнейм, переданный score или роль не дают полномочий.
- В активном ответе не раскрывать правильный TMDB ID, названия, aliases и будущие кадры; личные попытки и кадры не передавать другим игрокам.
- Секреты, `.env`, cookies, пароли, билеты и токены не добавлять в отслеживаемые файлы, логи или тексты ошибок.
- `.env.example` содержит только названия переменных, безопасные локальные значения и пустые placeholders секретов.
- Пароли комнат хранить как salted password hashes; opaque session tokens — как криптографические хеши.
- Проверять HTTP/WS Origin и membership, ограничивать размеры запросов и частоту чувствительных действий.
- Изменение HTTP API отражать в OpenAPI и contract tests; изменение realtime — в схемах и примерах WS-событий.

## Реализация и проверка

- Порядок: контракт и инфраструктура → TMDB/каталог → соло → лобби → матч → realtime и восстановление → передача контрактов фронтенду.
- Обновлять требования, план и задачи при согласованных изменениях поведения. Историю локального демо не переписывать как историю backend.
- Для игровых правил и исправлений сначала воспроизводить ожидаемое поведение тестом.
- Unit-тесты проверяют правила и проекции. HTTP/WS integration tests проверяют права, validation и сетевой контракт.
- Гонки, блокировки, дедлайны и восстановление после restart проверять на настоящем PostgreSQL; mock/SQLite этого не подтверждают.
- TMDB и часы можно подменять в тестах. Runtime mock-каталог в production запрещён.
- После появления tooling запускать type-check, lint, format check, подходящие тесты и build. Команды зафиксировать в README/package.json.
- Задачи отмечать выполненными только после проверки. В отчёте различать выполненные, непроверенные и заблокированные сценарии.
- Фактический запуск на двух физических устройствах и production cutover не объявлять проверенными по одним API-тестам.

## Рабочая область и Git

- Сохранять посторонние изменения; не применять destructive Git-команды и не обходить проверки.
- Git workflow закреплён в `docs/git-workflow.md`: постоянные `main`/`dev`, `feature/*` и `fix/*` от `dev`, checks и PR в `dev`.
- После принятого merge и checks поставить annotated уникальный `dev/<feature>-<PR-or-date-suffix>` на merge commit,
  опубликовать только этот тег, затем удалить только соответствующую merged feature/fix branch локально и remote.
- Релиз: обычный merge `dev` в `main` с сохранением ancestry, checks и annotated `vSemVer` на exact release commit.
  Только после успешной публикации версии удалять локально/remote `dev/*`, достижимые из exact version commit.
  Сохранять ещё не выпущенные dev-теги, `v*` и постоянные ветки. Опубликованные теги не перемещать.
- CI triggers для `dev/*` и `v*` раздельные. Сейчас документируется правило; автоматическая публикация/очистка не настроена.
- Принятый владельцем merge/release разрешает последующие шаги этой политики без повторного разрешения на каждый тег или удаление.
  Проверять все предусловия; уточнять только изменение области/полномочий.
- Новые внешние ресурсы и production требуют соответствующего запроса владельца.
- Yarn Classic 1.22, Prettier через `@afpia/prettier`, ESLint TypeScript; документация на русском.
- Коммиты: `<emoji> <type>(<scope>): <русский subject>`, например `✨ feat(solo): добавление серверной игры`.
